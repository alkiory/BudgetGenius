Seis candidatos

1

El backoffice es un archivo, no un módulo

Strong

presentation/pages/superadmin/backoffice.tsx · 2.644 líneas · 16 componentes top-level

Cuatro pestañas, el editor de páginas (640 líneas), el modal de módulo (253), el formulario de bloques generado por esquema y ProviderKeysSection conviven en un único archivo con 11 useState en la página raíz. Un cambio de una columna en Claves de Finny obliga a atravesar el editor de páginas; nada de esto se puede renderizar en un test sin montar la página completa. Es divergent change puro: el archivo cambia por cuatro razones no relacionadas.

Antes

backoffice.tsx 2.644
overview + módulos + editor + claves + avisos
  • 16 componentes con estado compartido
  • cambiar un tab toca el archivo entero
  • sin superficie de test

Después

overview/
modules/
page-editor/
api-keys/
notifications/
shared/forms
  • cada carpeta = un tab + su query
  • PageContentEditor con interfaz propia
  • se testea un tab aislado

Ganancia: localidad real. El editor de páginas pasa de «código dentro de una página» a módulo con interfaz { module, modules, blockTypes, onSave }, que es exactamente lo que un test necesita para existir.

2

«Aviso vivo» tiene tres definiciones distintas

Strong

application/notifications/announcement.service.ts · application/sync/sync.service.ts · application/superadmin/superadmin-overview.service.ts

La lectura exige published + publishedAt <= now() + expiresAt > now(). El resumen cuenta where: { published: true } y el poll de sync igual. Consecuencia: un aviso caducado o programado para el mes que viene aparece como vivo en el backoffice y despierta a todos los dispositivos al editarlo, porque MAX(updatedAt) no filtra nada.

Antes

AnnouncementService → ventana completa
overview → solo published
sync → solo published
  • tres criterios, un solo concepto
  • el contador del panel no cuadra con la app
  • editar un borrador invalida la caché de todos

Después

announcements/live.ts → una condición
lectura
conteo
revisión
  • un único predicado SQL compartido
  • el panel dice lo mismo que la app
  • + índice (publishedAt, expiresAt)

Ganancia: corrige un dato mostrado al operador y, de paso, quita ruido al poll: el cambio de un borrador deja de invalidar la caché de cada usuario.

3

El poll de sync hace 11 subconsultas por dispositivo cada 15 s

Strong

application/sync/sync.service.ts · infrastructure/use-cross-device-sync.ts · migración 1800000000015

Cada llamada son 11 scalar subqueries en una sola sentencia: 4 dispositivos = ~1.056 subconsultas por hora solo para saber si algo cambió. Dos de ellas son globales (app_notifications): MAX("updatedAt") no tiene índice —solo existe (published, publishedAt)— así que es un sequential scan en cada tick, para todos los usuarios.

Antes

11 subqueries · todas las tablas
2 sin userId, 1 sin índice
  • coste lineal con dispositivos
  • una edición de borrador despierta a todos

Después

1 CTE userId-scoped
caché Redis 5 s por usuario
índice app_notifications(updatedAt)
  • mismo contrato, coste acotado
  • N dispositivos del mismo usuario cuestan 1

Ganancia: el contrato no cambia (una cadena de revisión); cambia lo que cuesta sostenerlo. El deepening es mover la definición de «revisión» a un módulo que también es dueño de la caché, en vez de un SQL suelto en el servicio.

4

Las imágenes del catálogo viven en el disco del contenedor

Worth exploring

application/superadmin/media.service.ts · docker-compose.gce.yml · apps/api/.env.example

MediaService escribe en process.cwd()/uploads. UPLOAD_DIR=/data y su volumen solo existen en docker-compose.gce.yml: en cualquier otro despliegue (prod compose, Docker local, una segunda réplica) las imágenes caen en la capa del contenedor y desaparecen al recrearlo, dejando bloques apuntando a un 404. Tampoco hay limpieza de huérfanos al borrar un bloque.

Antes

GCE: /data + volumen ✓
otro host: /app/uploads → efímero
dos réplicas: dos catálogos de imágenes

Después

UPLOAD_DIR en .env.example + todos los compose
o almacén de objetos con URL firmada
barrido semanal de huérfanos

Ganancia: el catálogo deja de depender de dónde se despliegue. Es la diferencia entre «funciona en mi VM» y «funciona».

5

El resumen carga el catálogo entero para contar

Worth exploring

application/superadmin/superadmin-overview.service.ts · 14 consultas en paralelo

modules.find() trae todas las filas, incluido el jsonb content con secciones, bloques e imágenes de cada página, solo para incrementar cinco contadores. Lo mismo con apiKeys.find(). El resumen escala con el tamaño del contenido, no con el número de módulos.

Antes

14 queries · 2 find() completos
jsonb de páginas en memoria

Después

GROUP BY kind, status
count() de claves activas
sin leer content

Ganancia: el panel se abre igual de rápido con 5 módulos que con 500 páginas escritas.

6

La superficie nueva no tiene red de seguridad

Strong

apps/api/test/ (30 specs) · apps/webClient/tests/ (15 specs)

Hay app-module-rename, announcement-audience y user-seeder-superadmin, pero ningún test cubre failover de claves, updateContent (normalización de bloques y re-slug de ids), subida de imágenes, sync ni el backoffice. Es justo la lógica que se validó a mano y la que más fácil se rompe en silencio.

Antes

validación manual
rotar una clave, publicar un aviso, reordenar tabs

Después

unit: 401 → siguiente clave → FINNY_INVALID_KEY
unit: bloque desconocido / componente inexistente
E2E: crear módulo → aparece en /app/modules

Ganancia: tres tests baratos cubren el 80 % del riesgo nuevo. Ninguno necesita proveedor real ni navegador para los dos primeros.

Deuda pequeña, una línea cada una

  • AiService.getHistory hace JSON.parse sin guardia: un valor viejo o corrupto en Redis convierte cada prompt en un 500.
  • AppModuleService.update y .reorder escriben fila por fila sin transacción: un fallo a mitad deja tabs con orden parcial.
  • .env.example no lista SUPERADMIN_EMAIL, SUPERADMIN_PASSWORD ni UPLOAD_DIR, aunque el README los exija para producción.
  • AnnouncementService.findLiveForUser(userId) recibe un userId que no usa: la firma promete un filtro que ya no existe.
  • i18n sigue en dos JSON de 1.487 líneas sin claves tipadas: el compilador no puede avisar de una clave que falta.

Lo que conviene no romper

tsc -bGate real en CI, no el falso verde anterior
AES-256-GCMClaves de Finny cifradas y revelables solo por rol
0XSS: los bloques se normalizan por esquema y se renderizan como React

Recomendación

Empezar por el candidato 2, con el 3 detrás

Comparten la misma costura —qué significa «algo cambió para este usuario»— y se arreglan en una tarde: un predicado de aviso vivo compartido por lectura, resumen y sync; el conteo del panel alineado con la app; el poll con una sola consulta, caché corta e índice. Después el 6 (tres tests) para que el 1 se pueda partir sin miedo. El 1 es el que más paga a futuro, pero es refactor puro: sin tests primero, se rompe en silencio.
