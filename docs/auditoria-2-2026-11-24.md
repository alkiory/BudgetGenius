## 3. Qué quedó implementado para cerrar D2

### D2.1 — ventana exclusiva solo para gasto
- `BudgetRepository.findOverlapping(userId, startDate, endDate, type, excludeBudgetId?)` filtra por `type`.
- `BudgetService` solo valida en `spending` al crear, y al actualizar si cambia la ventana **o el tipo** (`savings → spending`).
- Un presupuesto de ahorro puede solapar con gasto o con otra meta; un gasto no se bloquea por un ahorro.
- Cobertura: 45 tests de servicio + flujo real en UI validado por ti (crear ahorro solapado sin toast).

### D2.2 — atribución explícita con FK
- **Migración** `1800000000012-TransactionBudgetCategoryLink`:
  - `transactions.budgetCategoryId integer NULL`;
  - FK `FK_transactions_budgetCategoryId` → `budget_categories(id)` con `ON DELETE SET NULL`;
  - índice `IDX_transactions_budgetCategoryId`;
  - backfill **solo** de filas con exactamente un candidato, solo gastos y solo presupuestos `spending`. Idempotente (columna/constraint/índice con `IF NOT EXISTS`, backfill solo sobre `NULL`).
- **Escritura** (`TransactionService#resolveBudgetCategoryId`):
  - ingresos (`amount >= 0`) nunca se vinculan;
  - un `budgetCategoryId` explícito debe pertenecer al usuario (404 si no);
  - si no hay id explícito, se vincula solo cuando hay un único candidato (ventana + nombre case-insensitive). La ambigüedad queda `NULL`.
  - las importaciones usan un `UPDATE` set-based (`linkUnambiguousBudgetCategories`) en lugar de N consultas.
- **Lectura** (`sumExpenseAmountsByBudget`): dos fuentes disjuntas que se suman por `(budgetId, categoría)`:
  1. filas vinculadas, por FK (inmune a renombrados y a cambios de ventana);
  2. filas `NULL`, con el fallback legacy ventana + nombre.
  Sumar ambas y excluir las vinculadas del fallback evita doble conteo.
- **Tests nuevos** (`apps/api/test/transaction-service.spec.ts`, 8 casos): vínculo único, ambiguo, ingreso, id explícito propio, id ajeno, edición que re-resuelve, gasto→ingreso que limpia el vínculo e importación con linker set-based.

### Residual importante
El backfill solo pudo vincular **10 de 604** gastos históricos. Los otros **594** no tienen una categoría de presupuesto con el mismo nombre dentro de la ventana (o están fuera de toda ventana). Esto es correcto por diseño —no se inventa historia— pero significa que:

- el beneficio de D2.2 hoy se concentra en transacciones nuevas;
- renombrar una categoría **sigue moviendo** el histórico no vinculado;
- el fallback por nombre sigue siendo el camino dominante en datos viejos.

Si se quiere cerrar también el histórico, hace falta una decisión de producto: pedir confirmación al usuario al renombrar, o una pantalla de “atribuir gastos sin presupuesto”. No es un bug de D2.2; es cobertura.

## 4. Hallazgos

### 4.1 P1 — El typecheck del frontend está en falso verde

`apps/webClient/tsconfig.json` es un config de solución:

```json
{ "files": [], "references": [{ "path": "./tsconfig.app.json" }, { "path": "./tsconfig.node.json" }] }
```

`package.json` define `"check-types": "tsc --noEmit"`. Con `files: []`, ese comando **no comprueba ningún archivo** y sale con código 0. El comando correcto es `tsc -b`. Al ejecutarlo aparecen **20 errores reales**, entre ellos:

- `useLoadUser.tsx`, `splash.tsx`: `_retry` no existe en `AxiosRequestConfig` (la augmentación de tipos no se está aplicando en el proyecto de app).
- `notification-settings.tsx`: `Switch` no acepta `onCheckedChange`.
- `personal-info-form.tsx`: `User | null` pasado a `Partial<User>`.
- `privacy-policy-page.tsx` / `terms-of-service-page.tsx`: `.map` sobre `$SpecialObject` (tipado de i18n).
- `onboardingPage.tsx`: `string` no asignable a `"en-US" | "es-CO"`.
- `splash.tsx`: `userId` declarado y no usado.

**Impacto:** CI no detecta deriva de tipos en el frontend; el build de Vite no falla por tipos. **Fix:** cambiar el script a `tsc -b` y corregir los 20 errores (1–2 h, en su mayoría tipos, no lógica). No lo he tocado en este turno porque excede el cierre de D2 y toca pantallas ajenas.

### 4.2 P1 — Índices ausentes en `transactions`
`pg_indexes` muestra en `transactions` solo la PK y el índice nuevo `budgetCategoryId`. No hay índice por `userId` ni por `(userId, date)`.

`GET /budgets` ejecuta ahora **dos** agregaciones sobre todas las transacciones del usuario (vinculadas + legacy). Con 681 filas es invisible; con decenas de miles será un seq scan por carga de la pantalla. El propio doc D2 ya lo marcaba como P1.

**Fix propuesto:** migración con `(userId, date)` y, si se quiere cubrir el path nuevo, `(userId, budgetCategoryId)`. Medir con `EXPLAIN` antes/después. No lo he añadido para no mezclar optimización con el cierre funcional.

### 4.3 P1 — Importación sin idempotencia
`POST /api/transactions/import` acepta hasta 1.000 filas y hace `insert` directo (`createMany`). Un reintento por timeout duplica el extracto completo. No hay clave de idempotencia ni dedupe por `(userId, date, amount, description)`.

**Impacto:** datos financieros duplicados, difíciles de detectar. **Fix:** idempotency key por request o dedupe explícito con reporte de “ya existían N”.

### 4.4 P1 — Throttle global de 4 req/10 s
`ThrottlerModule` aplica 4 peticiones cada 10 s por dispositivo/IP a **todas** las rutas. El dashboard dispara varios GET en paralelo (settings, budgets, transactions, overview) y una navegación rápida puede producir 429. En móvil con CGNAT se mitiga con `X-Device-Id`, pero el límite sigue siendo agresivo para lectura.

**Fix:** límites por ruta (lectura más alto, auth más estricto) o un bucket separado para GETs autenticados.

### 4.5 P1 — Documentación desincronizada
- `README.md` badge **v1.7.3**, tabla “NestJS 10”, diagrama con API en **3000** y Swagger en 3000; el código va por **1.10.0**, Nest **11** y puerto **5000**.
- `docs/changelog.md` termina en **v1.7.3**; faltan 1.8–1.10.
- `apps/webClient/lint_report.json` es un artefacto viejo con 59 errores que no refleja el lint actual y confunde cualquier auditoría.

**Fix:** reconciliación puntual del README (no reescritura), entradas 1.8–1.10 en changelog y borrar `lint_report.json` del repo.

### 4.6 P2 — Superficie expuesta
- **Swagger público:** `SwaggerModule.setup('docs', …)` se registra siempre; en producción queda `https://api…/api/docs` sin auth. Expone el mapa de endpoints. **Fix:** condicionar a `!isProduction` o protegerlo.
- **Remitente de correo sandbox:** `resend-mailer.service.ts` usa `BudgetGenius <onboarding@resend.dev>`. Además del branding, un dominio sandbox limita entregabilidad y destinatarios. **Fix:** verificar dominio propio y mover el remitente a variable de entorno.
- **Bind `0.0.0.0`:** correcto en contenedor, pero conviene que el proxy sea el único expuesto (revisar `docker-compose.prod.yml`).
- **CSP:** activa y razonable (`script-src 'self'`, `frame-ancestors 'none'`), con excepciones explícitas para Swagger y el shim OAuth. Sin `unsafe-eval`. Bien.

### 4.7 P2 — Capas y DTOs
- Los “domain entities” son entidades TypeORM con decoradores de persistencia; no hay puertos/interfaces de repositorio reales (se inyectan clases concretas). El README habla de “repository ports”, pero la abstracción es nominal. No es un incendio; sí explica por qué los tests mockean clases completas.
- `CreateTransactionDto` importa `@CreateDateColumn`/`@UpdateDateColumn` de TypeORM (decoradores de persistencia en un DTO) y declara `id` obligatorio aunque el endpoint lo omita. Es una fuga de capa y ruido para Swagger.
- `TransactionService#createTransaction` hace spread del DTO; `whitelist: true` lo protege, pero el contrato sería más claro con campos explícitos.

### 4.8 P2 — Testing
- 17 specs de API y 13 de Playwright; no hay tests unitarios de componentes/hooks del frontend (Vitest está instalado, pero no se usa para unidades).
- Los flujos que validaste a mano (tema, presupuesto de ahorro solapado) no tienen spec de UI; D2.1/D2.2 sí tienen unidad de servicio. Un Playwright de “crear ahorro solapado” sería barato y evitaría una regresión silenciosa.

### 4.9 Positivos que conviene no romper
- Cookies `HttpOnly`/`Secure`/`SameSite` en web y tokens **fuera de `localStorage`** en navegador (solo el WebView los persiste, por limitación real de cookies).
- Ownership en SQL (`userId` en WHERE) en transacciones, presupuestos y categorías; 404 en vez de 403 para no filtrar existencia.
- Migración D2.2 idempotente, con backfill conservador y reporte en el log.
- Separación lectura legacy/FK que evita doble conteo y mantiene números idénticos.
- `ValidationPipe({ whitelist: true, transform: true })` global y `ArrayMaxSize(1000)` en importación.

## 5. Arquitectura con ojos frescos

Aplicando el *deletion test* y buscando **localidad** (no “componentes” ni “servicios” genéricos):

1. **La atribución ya tiene localidad.** Antes estaba repartida entre la query de lectura y el nombre libre; ahora la regla vive en `TransactionService#resolveBudgetCategoryId` y el repositorio solo resuelve candidatos. Un cambio futuro (p. ej. atribución manual desde la UI) tiene un único sitio donde entrar. **Mantener.**
2. **`BudgetRepository` es el módulo más profundo y el más expuesto.** Concentra solapes, suma de gastos, categorías y ownership. Es útil, pero mezcla SQL de negocio con acceso. El siguiente *deepening* razonable no es partirlo en trozos pequeños: es extraer un **módulo de atribución/consumo** (`resolve`, `sum`, `reassign`) que hoy está repartido entre `TransactionService`, `TransactionRepository` y `BudgetRepository`. Solo merece la pena si aparece una tercera ruta que necesite atribuir (p. ej. edición masiva o reglas).
3. **La capa domain no es domain.** Si se quiere Clean Architecture real, habría que separar entidad de persistencia o aceptar explícitamente que el “domain” es el modelo ORM. Documentarlo es más barato que refactorizarlo.
4. **i18n es un módulo plano y enorme.** Dos JSON de >1.000 líneas con claves sin tipar; los errores de `.map` sobre `$SpecialObject` vienen de ahí. Un `t()` tipado por claves o un esquema de validación de locales evitaría clases enteras de bugs.
5. **La marca no tiene módulo.** 155 menciones de “budgetgenius” en código (38 en i18n), más dominios y correos. Un `brand.ts` con nombre, dominio, emails y remitente convertiría un rebrand de “grep y reza” en un cambio de configuración. Es la mejora con más leverage para el siguiente paso.

## 6. ¿Podemos implementar el “rewash” / cambio de imagen?

Sí. Conviene separar dos alcances porque el coste y el riesgo son distintos.

### 6.2 Dos alcances

**A. Rewash visual (misma marca, nueva imagen)** — recomendado como primer paso.
Cambiar paleta, tipografía, logo, iconos, splash y copy de landing. No toca identidad de tienda, dominios, OAuth ni base de datos.
**Estimación:** 1–2 días incluyendo revisión visual; riesgo bajo. Los tokens CSS ya están centralizados, así que el 80 % es diseño, no fontanería.

**B. Rebrand completo (nombre nuevo)** — viable, pero es un proyecto, no una tarde.
Incluye A + renombrar producto, dominio, correos, remitente, app Android y documentación.
**Estimación:** 1–2 semanas de trabajo efectivo + tiempos externos (verificación de dominio, revisión de tienda, propagación DNS).
**Riesgo principal:** `applicationId` de Android es inmutable para una ficha existente. Cambiarlo implica **nueva app en Play Store**, nueva ficha, nuevos installs y ningún camino de actualización para los usuarios actuales. Si la app ya está publicada, hay que decidir: (a) mantener `com.budgetgenius.mobile` y cambiar solo el nombre visible, o (b) asumir una migración de listing.

### 6.3 Bloqueos y dependencias externas
- **Google Cloud OAuth**: redirect URIs y origen autorizado del nuevo dominio.
- **Firebase**: proyecto/hosting y `google-services.json` atados al `applicationId`.
- **Resend**: verificar el dominio nuevo y actualizar SPF/DKIM; el remitente sandbox actual ya es una deuda.
- **Cookies/CORS**: `COOKIE_DOMAIN`, `FRONTEND_URL` y la allowlist de `cors.ts` deben cambiar juntos o la sesión se rompe.
- **Legal**: privacidad/términos y correos de contacto deben apuntar al dominio nuevo antes de publicar el cambio.
- **BD**: `DB_NAME=budgetgenius*` puede quedarse; es interno y no se ve.

### 6.4 Plan por fases propuesto

| Fase | Contenido | Salida |
|---|---|---|
| 0. Decisión | ¿Rewash visual o rename? ¿Se conserva `applicationId`? | Alcance cerrado |
| 1. Fundación | `brand.ts` (nombre, dominio, emails, remitente) + tokens CSS + logo SVG | Una sola fuente de verdad |
| 2. Web | i18n, landing, legal, PDF/Excel, favicon/título | Web con imagen nueva |
| 3. Móvil | iconos/splash, `strings.xml`, nombre visible; `applicationId` solo si se decidió B | APK reconstruida |
| 4. Infra | Dominio, TLS, OAuth, Firebase, Resend, CORS/cookies | Producción con identidad nueva |

**Recomendación:** hacer **A (rewash)** ahora con la fase 1 incluida, y decidir B por separado cuando exista estrategia de tienda. El rediseño visual no bloquea D2 ni requiere migraciones; el rename sí exige una ventana de mantenimiento y coordinación externa.

### 6.5 Dirección visual (si se hace rewash)
El producto es una app financiera personal, no un dashboard corporativo. La identidad actual (violeta/magenta, Playfair Display) ya es distintiva y no cae en el azul SaaS genérico. Un rewash con sentido debería:
- conservar **una** familia display con carácter y una sans neutra para datos;
- usar el color como señal (verde/rojo) y no como decoración en cada tarjeta;
- reducir el ruido de bordes/sombras repetidos y dar jerarquía por tipografía y espacio;
- mantener contraste AA y foco visible (hoy hay `focus-visible` en varios controles, pero no está auditado en toda la app).

No he generado propuestas visuales en este turno; el documento deja el alcance y el coste, no el diseño.
